## ⛔ Публикационный предохранитель (MUST, без свободы трактовки)

Правило сформулировано **через свойство информации, а не через канал** (#189, D-038):
recon-поверхность экосистемы — это **и сайт, и сам публичный репозиторий** (все
отслеживаемые файлы: канон, документация, каталог, workflow'ы, письма, handoff), **и логи
прогонов GitHub Actions** (у публичного репо они публичны; маскируются только `secrets`,
и только точное вхождение значения целиком — производные формы вроде короткого
хостнейма из `journalctl` утекают, G290). Не кладём ни в один из этих каналов никогда:

1. **Реальные данные на скриншотах** — ФИО сотрудников, контрагенты, цены, номера договоров. Снимать только на демо/обезличенных данных либо замазывать **до** съёмки, а не после.
2. **Инфраструктурные детали** — хостнеймы и имена боксов, технические домены хостера, имя хостера, порты, внутренние URL, пути на сервере, состав жильцов, имена SSH-алиасов и ключей, объём памяти боксов. Показывать только продуктовые прод-URL на собственных доменах, которые и так публичны. В CI такие значения живут в `secrets` (не в `vars` — они печатаются в лог), а шаги диагностики печатают урезанный вывод (`journalctl -o cat`, `systemctl show -p …`), не полный дамп.
3. **Код закрытых репо** — по приватным проектам скриншот + описание функционала, не фрагменты кода.

Правило одной фразой: **репозиторий и сайт показывают, что система умеет, а не как она устроена изнутри и на ком работает.** Сомневаешься по конкретному экрану или строке — не публикуй: задай вопрос владельцу и дождись явного ответа. Форма вопроса любая (тем механизмом, который есть у агента), сам шаг обязателен.

Проверка «чисто» делается **грепом по содержимому, не памятью**, в обеих письменностях
(термины двуписьменны: хостер, боксы, проекты), и каждому пустому результату должен
предшествовать непустой контроль тем же шаблоном и инструментом (#262). Слепые пятна
Git Bash под Windows: `grep -i` не матчит кириллицу (G286), аргумент с ведущим `/`
превращается в windows-путь (G288 — `MSYS_NO_PATHCONV=1` или `[/]etc/...`).
Исторические записи (handoff, отправленные письма) при чистке не переписываются —
вычистка ничего не отзывает, это гигиена на будущее.

Технические правила витрины:

- Скриншоты прод-сайтов собирать методом pool #079 — puppeteer-core headless + системный Chrome; счётчики Метрики (`mc.yandex.ru`) и LiveInternet (`counter.yadro.ru`) резать перехватом запросов до съёмки (иначе накрутка чужой статистики + зависание `networkidle2`). Не руками.
- Все исходящие абсолютные URL (canonical, OG, share-ссылки) — **punycode** через `new URL(u).href` (G133/G134: юникод-IDN ломает сниппеты ВК).
- Кнопка «Сервисы Малмыжа» → `https://вход.вмалмыже.рф/services` (в коде punycode `https://xn--b1ae3a1a.xn--80adkdyec4j.xn--p1ai/services`) закладывается на этапе вёрстки; запись сайта в каталог — при go-live.

## 📬 Mailbox-протокол (ADR-0001 v3) — проверка ДО любой другой работы

| Направление | Кто пишет | Где |
|---|---|---|
| `brain → Портфолио` | brain | `../brain_matrica/mailboxes/ValentinPortfolio/from-brain/*.md` — читается из **двух каналов** (локально + GitHub API, § ниже) |
| `Портфолио → brain` | мы | **`mailbox/to-brain/*.md`** в этом репо (через PR) |

Сканить только корень `from-brain/` (не `DRAFTS/`, не `ARCHIVE/`). Compliance: `mandate`→MUST, `recommend`→SHOULD, `suggest`→MAY.

**Двухканальное чтение входящего mailbox (мандат владельца 2026-08-04):** brain_matrica
синхронизирующим командам не подвергается вообще, входящие письма читаются из двух
независимых источников и **объединяются** (видимое только на GitHub — такое же «новое»,
как видимое только локально):

1. **Локально:** корень `../brain_matrica/mailboxes/ValentinPortfolio/from-brain/*.md`.
2. **GitHub API/веб** (без clone/fetch/pull): `gh api "repos/Valstan/brain_matrica/contents/mailboxes/ValentinPortfolio/from-brain"` → список имён; содержимое письма — raw: `gh api -H "Accept: application/vnd.github.raw" "repos/Valstan/brain_matrica/contents/mailboxes/ValentinPortfolio/from-brain/<file>.md"`.

Правило свежести для одноимённого письма в обоих источниках — по истории **именно этого
пути**, не репозитория целиком: локальная версия с незакоммиченными изменениями — более
свежий кандидат; иначе последний локальный коммит файла (`git log -1 --format=%ct -- <path>`)
против последнего коммита пути на GitHub. Порядок надёжно не определяется — прочитать обе
версии, явно отметить конфликт, **ничего не перезаписывать**. Свежесть одного письма/репо
на другие не переносится.

Формат `mailbox/to-brain/YYYY-MM-DD-slug.md`:

```yaml
---
from: ValentinPortfolio
to: brain
date: YYYY-MM-DD
topic: ...
kind: idea | question | feedback | report
compliance: suggest | recommend | mandate   # для kind=idea
urgency: low | normal | high
---
```

## Начало и завершение работы

В начале работы:

1. Синхронизируй **только этот** репозиторий (`git fetch`, затем безопасный fast-forward при чистом дереве). Чужие репо (в т.ч. `brain_matrica`) не синхронизировать вообще.
2. Прочитай входящие `../brain_matrica/mailboxes/ValentinPortfolio/from-brain/*.md` **двухканально** (локально + GitHub API, §📬) и объедини наборы.
3. Прочитай `docs/SESSION_HANDOFF.md` и проверь `git status`/последние коммиты. В Claude Code это делает хук `SessionStart` (`.claude/scripts/session_start.sh`, только чтение, без сети) — если его вывод уже в контексте, повторно читать не нужно.

**Сессия = одна нитка, не один день** (D-066). Handoff пишется **по шагам нитки**, а не
только при закрытии: сделал шаг — обновил в `docs/SESSION_HANDOFF.md` строку `Updated:`,
«где мы» и «что дальше», и это уезжает **тем же PR**, что и сам шаг. Мерж — по зелёному
гейту, не по команде владельца. `/close_session` — страховка на случай, когда шаг сделан
словами в чате и в файлы не попал, при смене машины или когда handoff распух.
Восстановление после обрыва — из Git/PR/handoff, не по памяти чата; отдельной команды для
этого нет.

Подробные исполняемые памятки лежат в `.claude/commands/start.md` и `close_session.md`;
несмотря на имя каталога, их workflow применим к любому агенту. При любом PR в
`AGENTS.md` — diff-чек обеих команд, чтобы они не разошлись с каноном. Правило чтения
памяток для любого агента:
`allowed-tools:` игнорировать; `/команда` = «выполни шаги файла»; `AskUserQuestion: «…»` =
«задай вопрос и дождись явного ответа» — **форма любая, шаг обязателен**.

## Git и совместная работа нескольких агентов

- `main` защищён **сервером** (включено brain 2026-08-17, `enforce_admins: true`): прямой
  push отклоняется, force-push и удаление ветки запрещены. Порядок прежний: ветка →
  коммит → push → PR → squash merge. `reset --hard` на `main` запрещён и правилом тоже.
- За защитой стоит **PR-гейт**: workflow `CI`, job **`gates`** на `pull_request` —
  сканер секретов (gitleaks, `--redact`, полная история), typecheck, сборка static export
  и проверка полноты экспорта. Имя job'а — то, что brain выставляет обязательной
  проверкой: **не переименовывать, не предупредив письмом**, иначе PR повиснут навсегда
  в ожидании отчёта, которого никто не пришлёт.
- Один агент — одна задача, отдельная ветка и, при одновременной работе, отдельный
  `git worktree`. Не запускай двух пишущих агентов в одном рабочем дереве.
- Перед правкой проверяй `git status`. Незнакомые изменения считай чужими: не удаляй,
  не форматируй попутно, не включай в свой коммит и не прячь в stash.
- Не переключай ветку в рабочем дереве, которое может использовать другой агент.
- Объявляй границы файлов/задачи в описании PR. Если границы пересекаются, второй агент
  ждёт merge первого и ребейзит/обновляет свою ветку до начала правок.
- Один PR должен решать одну задачу. Коммиты — Conventional Commits.
- После обрыва сначала восстанавливай фактическое состояние из Git/PR, не повторяй
  действия по памяти.

## Текст — файлом, не в командной строке (D-046, MUST)

**Не сочиняй текст внутри командной строки.** Текст, написанный в команде, проходит до
четырёх парсеров (кавычки инструмента → шелл, на Windows их два с разным синтаксисом →
удалённый шелл при `ssh` → кодовая страница консоли), и отказ выглядит как ошибка в
данных, а не в доставке. Содержимое пишется инструментом записи файлов, команде отдаётся
**путь**:

| Задача | Вместо | Правильно |
|---|---|---|
| Скрипт / патч / конфиг | `cat <<'EOF' > f` | записать файл инструментом записи |
| Commit message | `-m` с переносами / кириллицей | файл → `git commit -F msg.txt` |
| PR / issue body | `--body "…"` | файл → `gh pr create --body-file body.md` |
| HTTP-тело | heredoc в `curl` | файл → `curl --data-binary @body.json` |
| Файл на удалённый хост | heredoc через `ssh` | `scp` |

Триггер: в собственной команде появился перенос строки, backtick, `$`, кавычка или
не-ASCII — переписать через файл, не экранировать. Однострочные ASCII-команды без
кавычек внутри правило не затрагивает. Временные файлы — в scratchpad, не в репо.

Git — механизм координации между моделями; чат одной модели не является источником
истины для другой. Долговечные решения живут в документации/ADR, состояние незавершённой
работы — в `SESSION_HANDOFF`, история — в коммитах и PR.

## Какие AI-файлы хранить в Git

Коммитить:

- `AGENTS.md` — общие правила и источник истины;
- `CLAUDE.md`, `GEMINI.md` — короткие адаптеры к `AGENTS.md`;
- `.claude/commands/` и `.claude/settings.json` — общие безопасные команды/ограничения;
- `docs/SESSION_HANDOFF.md`, проектную документацию и `mailbox/`.

Не коммитить:

- локальные разрешения и персональные настройки (`.claude/settings.local.json`);
- кэши/сессии `.codex/`, `.gemini/` и временные планы вне проектной документации;
- `.env*`, ключи, токены, логи и временные файлы.

Секреты не должны жить в репозитории даже под защитой `.gitignore`.
